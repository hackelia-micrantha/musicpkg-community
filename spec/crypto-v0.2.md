# MUSICPKG v0.2 Cryptographic Profile

Status: Working Draft

This document freezes the byte-level cryptographic constructions used by the v0.2 interoperability profile. It is subordinate to the product/trust invariants in `architecture/invariants.md`.

## 1. Encoding and hash conventions

`CDE(x)` means the RFC 8949 Core Deterministic Encoding of CBOR data item `x`.

Requirements:

- definite-length CBOR only;
- shortest/preferred integer and length encodings;
- map keys sorted by bytewise lexicographic order of their deterministic encodings;
- duplicate map keys rejected;
- security-sensitive maps use the integer labels defined by `spec/musicpkg-v0.2.cddl`;
- unknown fields are rejected unless a future negotiated profile explicitly permits them.

`H(x)` means SHA-256 over exact byte string `x`.

Unless stated otherwise, hashes of MUSICPKG structured objects are SHA-256 over their exact CDE bytes.

## 2. Identifier/hash derivations

```text
media_hash             = H(CDE(media-descriptor))
content_manifest_hash  = H(CDE(content-manifest))
owner_key_set_hash     = H(CDE(owner-key-set))
validator_set_hash     = H(CDE(validator-set))
ledger_genesis_hash    = H(CDE(ledger-genesis))
record_hash            = H(CDE(ledger-record))
checkpoint_id          = H(CDE(checkpoint-payload))
```

Issuer identity is domain-separated:

```text
issuer_id = H( UTF8("MUSICPKG issuer v1") || 0x00 || issuer_ed25519_public_key )
```

Each state-changing record creates one current title output. Its identifier is:

```text
output_id = H(CDE([
    "MUSICPKG output-id v1",
    record_hash,
    0
]))
```

The terminal integer is an output ordinal reserved for future multi-output records. v0.2 requires it to be zero.

`package_id`, `track_id`, `grant_id`, `transfer_id`, and transition IDs are uniformly random identifiers of the sizes defined by the CDDL and MUST be generated by a CSPRNG.

## 3. Core algorithm profiles

### I1 / O1 signatures

Publisher profile I1 and owner profile O1 use Ed25519.

Owner profile O1 contains:

- Ed25519 public signing key;
- X25519 public HPKE/KEM key.

The associated private recovery material is exactly 64 bytes:

```text
Ed25519 32-byte seed || X25519 32-byte private key
```

### E1 owner envelope

RFC 9180 HPKE Base mode:

```text
mode = Base
KEM  = 0x0020  DHKEM(X25519, HKDF-SHA256)
KDF  = 0x0001  HKDF-SHA256
AEAD = 0x0002  AES-256-GCM
```

The recipient public key is the X25519 key from the destination `owner-key-set`.

```text
info      = UTF8("MUSICPKG owner-envelope E1")
aad       = CDE(owner-envelope-context)
plaintext = K_album   ; exactly 32 bytes
```

`enc` and `ciphertext` are stored exactly as emitted by RFC 9180. For E1 these are 32 and 48 bytes respectively.

### Device grant S1

RFC 9180 Base mode with the same X25519/HKDF-SHA256/AES-256-GCM suite as E1.

```text
info      = UTF8("MUSICPKG device-grant S1")
aad       = CDE(device-grant-body)
plaintext = K_album
```

### Device grant H1

RFC 9180 Base mode:

```text
KEM  = 0x0010  DHKEM(P-256, HKDF-SHA256)
KDF  = 0x0001  HKDF-SHA256
AEAD = 0x0002  AES-256-GCM
```

The P-256 public key is the 65-byte uncompressed SEC1 representation.

```text
info      = UTF8("MUSICPKG device-grant H1")
aad       = CDE(device-grant-body)
plaintext = K_album
```

Hardware attestation is not part of H1 playback validity.

## 4. Package and track keys

`K_album` is a uniformly random 32-byte package content key generated by a CSPRNG.

Every track uses an independently derived AES-256 key:

```text
salt = H(
    UTF8("MUSICPKG track salt v1") ||
    0x00 ||
    package_id
)

info = CDE([
    "MUSICPKG track key v1",
    package_id,
    track_id
])

K_track = HKDF-SHA256(
    IKM  = K_album,
    salt = salt,
    info = info,
    L    = 32
)
```

A `track_id` MUST be unique within a `package_id`.

## 5. Authenticated media records

v0.2 mandatory media-record AEAD is AES-256-GCM.

Maximum plaintext per record is 1,048,576 bytes.

For record number `i`:

```text
nonce = 0x00000000 || uint64_be(i)
```

Because `K_track` is unique to `(package_id, track_id)`, nonce uniqueness depends only on never reusing a record number for that track key.

Associated data is:

```text
record_aad = CDE([
    "MUSICPKG media record v1",
    package_id,
    track_id,
    i,
    plaintext_length,
    media_hash
])
```

Encryption:

```text
ciphertext_record = AES-256-GCM-Seal(
    key       = K_track,
    nonce     = nonce,
    plaintext = plaintext_record,
    aad       = record_aad
)
```

The 16-byte GCM authentication tag is appended to the ciphertext by the AEAD representation. A player MUST authenticate an entire record before releasing any plaintext from that record to the codec layer.

Records are concatenated in strictly increasing record-number order. The authenticated track index describes offsets and plaintext lengths; implementations MUST additionally validate that offsets are contiguous and consistent with `plaintext_length + 16` ciphertext record sizes.

## 6. Recovery envelope

The purchaser Recovery Root (`RR`) is a uniformly random 32-byte secret independent of owner keys.

Package recovery key:

```text
K_recovery = HKDF-SHA256(
    IKM  = RR,
    salt = package_id,
    info = CDE([
        "MUSICPKG recovery key v1",
        title_id,
        owner_key_set_hash
    ]),
    L = 32
)
```

Recovery AAD:

```text
recovery_aad = CDE([
    "MUSICPKG recovery-envelope v1",
    package_id,
    title_id,
    owner_key_set_hash
])
```

The nonce is a fresh random 12-byte value generated by a CSPRNG. It MUST NOT repeat for the same `K_recovery`.

Plaintext is the exact 64-byte O1 private material described above.

```text
ciphertext = AES-256-GCM-Seal(
    K_recovery,
    nonce,
    owner_private_material_o1,
    recovery_aad
)
```

Result length is exactly 80 bytes.

## 7. R1 passphrase recovery bundle

R1 protects the 32-byte Recovery Root for portable backup.

The KDF is RFC 9106 Argon2id with the second recommended profile:

```text
Argon2 type     = id
version         = 0x13
memory          = 65536 KiB
iterations      = 3
parallelism     = 4
salt            = 16 random bytes
output          = 32 bytes
```

The cryptographic input is a byte string. A text UI for R1 MUST encode the user's passphrase as UTF-8 after Unicode NFC normalization. Implementations SHOULD preserve/test the exact resulting bytes during backup creation to avoid recovery ambiguity.

The resulting 32-byte Argon2id output is `K_R1`.

R1 AAD is CDE of the KDF/profile fields before nonce/ciphertext:

```text
r1_aad = CDE([
    "MUSICPKG recovery-bundle R1",
    version,
    profile,
    argon2_type,
    argon2_version,
    salt,
    memory_kib,
    iterations,
    lanes
])
```

A fresh random 12-byte AES-GCM nonce is stored in the bundle.

```text
encrypted_RR = AES-256-GCM-Seal(K_R1, nonce, RR, r1_aad)
```

R2 threshold recovery and R3 compartmenting remain architecture profiles but are not mandatory wire profiles in v0.2.

## 8. Device-grant owner signature

After HPKE creation, the durable owner signs:

```text
device_grant_signing_input = CDE([
    "MUSICPKG device-grant signature v1",
    device-grant-body,
    enc,
    ciphertext
])
```

The signature is Ed25519 under the current O1 owner signing key.

A player MUST verify this signature and the owner binding before opening a device grant.

## 9. Ownership/transition signatures

All signatures below use Ed25519 and exact CDE bytes.

### Transfer

Seller:

```text
CDE(["MUSICPKG transfer seller v1", transfer-body])
```

Recipient:

```text
CDE(["MUSICPKG transfer recipient v1", transfer-body])
```

### Inheritance

Predecessor/recovery authority profile:

```text
CDE(["MUSICPKG inherit authority v1", transfer-body])
```

Heir:

```text
CDE(["MUSICPKG inherit heir v1", transfer-body])
```

### Reissue

Current owner:

```text
CDE(["MUSICPKG reissue owner v1", reissue-body])
```

Authorized reissuer/publisher:

```text
CDE(["MUSICPKG reissue issuer v1", reissue-body])
```

### Rekey/recovery

Old/recovery authority evidence profile:

```text
CDE(["MUSICPKG rekey authority v1", rekey-body])
```

New owner:

```text
CDE(["MUSICPKG rekey new-owner v1", rekey-body])
```

## 10. Ownership proof signature

```text
ownership_proof_signing_input = CDE([
    "MUSICPKG ownership-proof v1",
    ownership-challenge
])
```

The claimant signs with the Ed25519 key from the claimed current/historical `owner-key-set`.

The challenge nonce MUST be fresh and verifier-generated. A verifier MUST reject an expired challenge when `expires_at` is present and MUST reject audience/purpose mismatches.

## 11. Publisher issuance signature

`ownership/issuance.cose` is COSE_Sign1 with an inline payload equal to exact `CDE(issuance-payload)`.

Protected headers MUST contain:

```text
1 (alg) = -8   ; EdDSA
4 (kid) = first 16 bytes of H(issuer Ed25519 public key)
```

The unprotected header map MUST be empty in v0.2. COSE external AAD is the empty byte string. The signature uses Ed25519 according to RFC 9052/9053.

Trust in the issuer public key is a producer/ecosystem trust-policy question; cryptographic verification of the signature itself is mandatory.

## 12. Ledger record/state hashing

Record history uses the RFC 9162 Merkle Tree Hash construction with SHA-256:

```text
leaf hash = SHA-256(0x00 || CDE(ledger-record))
node hash = SHA-256(0x01 || left_hash || right_hash)
```

`records_merkle_root` is the RFC 9162 tree root over all ledger records in canonical ledger order.

The current-title state tree uses the same construction over exact CDE `ownership-output` leaves sorted by ascending `title_id`. There MUST be at most one current state leaf for a given `title_id`.

`state_root` is the resulting root. `output_count` is the number of current title outputs.

## 13. Checkpoint signatures and validator rotation

Each validator signs:

```text
checkpoint_signing_input = CDE([
    "MUSICPKG checkpoint v1",
    checkpoint-payload
])
```

Signatures are Ed25519. Validator signature arrays are strictly sorted by `validator_id`; duplicate validator IDs are invalid.

A checkpoint is finalized only when signatures from the validator set named by `validator_set_hash` meet that set's threshold and the deployment consensus/finality safety rules.

If checkpoint height `h` commits `next_validator_set_hash`, the next finalized checkpoint using the new set MUST be accompanied by that `validator-set` object and verification evidence showing:

```text
H(CDE(new_validator_set)) == old_checkpoint.next_validator_set_hash
```

The wire verifier need not implement the deployment's BFT network protocol; it MUST verify finalized checkpoint signatures, threshold/quorum policy, hash-linked checkpoint history supplied in the proof chain, and validator-set transitions.

## 14. Transition validity and output construction

For ISSUE, the created ownership output has sequence `0`.

For TRANSFER, INHERIT, REISSUE, and REKEY, the input output MUST be current/unspent in the deterministic state transition and the new output sequence is:

```text
new_sequence = input_sequence + 1
```

The new `ownership-output.producing_record_hash` is `H(CDE(record))`; `output_id` is derived as specified in section 2.

TRANSFER and INHERIT preserve `asset_id`, `title_id`, and normally `package_id`.

REISSUE preserves `asset_id` and `title_id` but changes `package_id` to the newly issued package.

REKEY preserves `asset_id`, `title_id`, and `package_id` while replacing owner key material/envelopes.

A transition is invalid if its body conflicts with the referenced input output, transfer policy, package lineage, owner signatures, or envelope commitments.

## 15. Algorithm agility

Every algorithm-bearing structure contains an explicit profile/version. Unknown mandatory profiles MUST be rejected rather than silently downgraded.

Future profiles may add post-quantum/hybrid KEMs, alternate AEADs, or new signature algorithms without changing the ownership/product model. v0.2 implementations MUST implement the profiles marked mandatory above.
